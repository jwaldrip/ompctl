What it is

A daemon, a paired device, and the sessions between them

ompd runs where your code is. It owns the agent sessions, the working directories, and the credentials. Pairing a device mints one scoped token for that device and nothing else, so a phone can be allowed to read and prompt without being allowed to create sessions or approve tool calls.

The console is the same application on every surface, which is why the phone and the desktop show the same state in the same colours. Six of them, each meaning exactly one thing about a session: whether it is working, waiting on you, or stopped.

Get started

Four commands and a code

Everything below runs on the machine that holds your code. The daemon binds to loopback unless you tell it otherwise, so nothing is reachable until you decide it should be.

  1. Install the daemon

    Builds ompd and puts it on your path, then loads it as a launch agent so it comes back after a reboot. 

    $ ompd self-install
$ ompd install

  2. Start it where your phone can reach it

    Loopback is the default. Give it an address on your network when you want to pair a device on the same wifi. Anything that can reach that address can ask the daemon to run code as you, and only a paired token stands in front of it. 

    $ ompd start --host 192.168.1.20
ompd is listening at http://192.168.1.20:7788
  Reachable from this network at:
    ws://192.168.1.20:7788/v1/socket

  3. Pair the device

    pair prints a six digit code that expires in ten minutes and can be spent once. approve turns it into a token, printed one time and never recoverable. On one machine, ompd invite does both and shows a QR code. 

    $ ompd pair "my phone" --scopes read,prompt
code    386707
$ ompd approve 386707 --scopes read,prompt

  4. Point the app at it

    Paste the endpoint and the token into the pairing screen, or scan the code the invite printed. The app lands on the sessions the daemon already holds. If nothing is there yet, start one on the machine with ompd new .

Scopes

A device gets exactly what you gave it

Scopes are set when the pairing is approved and are checked on every request. A device paired for reading and prompting cannot create a session or answer a clearance, and the console hides those controls rather than showing them and failing.

The four scopes, and what a device holding one can do.
Scope What it allows
read List sessions and read their transcripts.
prompt Send a message to a session and interrupt a turn in flight.
manage Create and archive sessions.
approve Answer a clearance, and invite another device.

Revoking a device stops its token on the next request or frame. There is no grace period, and the daemon keeps only a hash of the token it issued.
